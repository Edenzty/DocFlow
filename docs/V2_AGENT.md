# DocFlow v2：有边界的只读支持 Agent

v1 保留为冻结基线；`model.py` 和旧评测结果没有改写。v2 的 `SupportAgent` 使用真实的工具调用协议，在检索与最终草稿之间增加有限次数的自主查询和证据展开。它仍然不能审核或提交，实际提交由独立的人工审核工作流控制。

## 一条请求怎样走

1. 工作流提供初始证据和当前工单上下文。
2. 模型可以调用 `search_knowledge(query, method)`，用关键词、向量或混合检索继续查找，每次最多 5 条。
3. `expand_evidence(chunk_ids)` 只能展开先前实际返回过的片段；应用把对应证据交给只读后端，取回带原始 ID 的邻近片段。
4. `get_ticket_context()` 没有工单 ID 参数，只能读取当前请求已经提供的上下文白名单。
5. 模型返回严格的结构化草稿；应用检查字段、证据 ID 和原文引文，随后进入独立人工审核。

每次运行最多 3 次模型请求、6 次只读工具调用，证据池最多 15 条。最后一轮不提供工具；仍返回工具调用或无法生成有效草稿时，运行失败，不保存可审核草稿。工具请求超出上限的整批操作不会执行。未知工具、写入工具、越界 ID、额外参数和非法检索方式会被拒绝并写入调用轨迹。

## 草稿与引文存在性检查

最终模型输出必须严格包含：

```json
{
  "decision": "answer",
  "claims": [
    {
      "text": "归属检查失败会返回403。",
      "quotes": [
        {"chunk_id": "本次实际返回的ID", "quote": "实际文档中的连续原文"}
      ]
    }
  ],
  "questions": [],
  "reason": ""
}
```

`answer` 只能由 `claims[].text` 拼接，不能另外夹带一个未引用的自由回答字段。每条 claim 必须有实际证据中的原文，最多 5 个不同引用 ID。`needs_info` 和 `out_of_scope` 必须没有 claims，保留对应分类；前者还必须提出具体追问。

`quality.validation` 固定写为 **`quote_presence_only`**。这只证明引文出现在本次实际证据里；即使原文存在，也不能自动证明它支持 claim 的结论。`verified_quotes` 不是事实正确、语义蕴含或可自动提交的认证。审核人仍须逐条比较主张、原文及文档版本。测试特意保留“原文真实但主张可能无关”的例子，防止把此检查包装成语义评测。

## 模拟模式和真实模式

- 默认离线 Agent 是确定性的流程夹具，实际调用本地只读检索、上下文和证据展开，最后只摘录文档；页面与草稿明确标注离线。它不是大模型，也不能用于宣称真实 Agent 的回答效果。
- 真实模式通过 DeepSeek Chat Completion 的工具调用返回 `tool_calls`；应用执行白名单函数，再把带对应 `tool_call_id` 的工具结果送回模型。工具描述不是执行权限，实际权限始终由应用检查。
- 固定 HTTPS 地址，关闭环境代理继承与重定向，设置连接/读取超时；不做隐式 HTTP 重试。每次网络尝试前原子预留一次全局预算，超时和错误也计数。v1、v2 共用原有 40 次预算，不重置，不额外扩容。
- HTTP 成功与有效草稿是不同状态：请求使用量记录服务调用完成/网络失败，Agent 轨迹额外记录结构校验或引文检查失败。
- 轨迹记录步骤、状态、耗时、已脱敏的白名单参数和结果片段 ID；不记录请求头、密钥或原始模型异常。文档和工具结果用 `UNTRUSTED_DATA` 包裹、截断且受数量限制。

## 本地验证

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_agent.py -q
```

测试完全离线，通过注入客户端/HTTP 传输模拟正常响应、工具越权、文档诱导、非法引文、JSON 错误、轮次上限、预算耗尽和网络失败。测试注入客户端不会消耗真实 API 预算。新增的真实模型冒烟记录应另外保存，不能用离线夹具结果替代。

协议实现参考 [DeepSeek 官方工具调用说明](https://api-docs.deepseek.com/guides/tool_calls/)。该项目使用稳定 Chat Completion 地址及应用侧严格校验，没有声称启用需 `/beta` 的服务端 strict 模式。
